# FORTRESS-H3 — Production Security Hardening

Focused hardening story: production must fail safely instead of merely
logging a warning when known-insecure defaults are in play. No auth model
redesign, no new dependencies, no scoring/trading changes.

## 1. Previous unsafe/default behavior

| Value | Previous behavior |
|---|---|
| `FORTRESS_JWT_SECRET` | Missing/default → logged a `WARNING` and continued **only in non-local-dev deployments already had a partial guard**: `engine/auth_utils.py` already raised `RuntimeError` at import time if the secret was the hardcoded default *and* `FORTRESS_DB_BACKEND` wasn't `sqlite`/`local`. This part was already correct before H3 — see §8 below. |
| `FORTRESS_APP_PASSWORD` | Missing → logged a `WARNING` (`engine/routers/auth.py`) and continued regardless of environment. **No fail-fast path existed at all** — a real production deployment could run indefinitely with the publicly-known `fortress123` admin password. |
| CORS | No validation at all on the resolved `allow_origins` list. The unset-env default was already safe (localhost only, never a wildcard), but an operator setting `FORTRESS_CORS_ORIGINS=*` by mistake had nothing catching it. |
| Centralized validation | None — the JWT check lived only in `auth_utils.py`, the password check only in `routers/auth.py`, using two separately-written copies of "is this a known-unsafe value" logic. |

## 2. Final production behavior

- **`is_production_environment()`** (`engine/utils/security_config.py`) is
  the single production-mode signal: `FORTRESS_DB_BACKEND` not in
  `{"sqlite", "local"}` = production. This mirrors the exact convention
  `utils/db.py`'s pre-existing `_sqlite_only_mode()` already used for the
  same variable — no second, competing flag was introduced.
- **Production** (`is_production_environment() is True`): `RuntimeError`
  at import time, before any request is served, if —
  - `FORTRESS_JWT_SECRET` is missing, blank, the hardcoded dev default, or
    a generic placeholder (`changeme`, `secret`, `your-secret-key`, ...);
  - `FORTRESS_APP_PASSWORD` is missing, blank, the hardcoded `fortress123`
    default, or a generic placeholder (`password`, `admin`, `admin123`, ...);
  - the resolved CORS origin list contains a wildcard (`*`).
- **Development** (`is_production_environment() is False`): unchanged —
  logs a `WARNING` for each unsafe value and continues, so
  `FORTRESS_DB_BACKEND=sqlite` local runs still need zero configuration.
- No exception or log line generated by this story ever includes the
  actual secret/password value — every message names the environment
  variable, not its contents (see §7, and `test_G_*` in
  `tests/backend/test_security_config.py`).

## 3. Files changed

- `engine/utils/security_config.py` (**new**) — `is_production_environment()`,
  `validate_jwt_secret()`, `validate_admin_password()`,
  `validate_cors_origins()`, and the centralized
  `validate_security_configuration()`. This is the one place that knows
  what "unsafe" means for each value.
- `engine/auth_utils.py` — JWT-secret check now calls
  `is_production_environment()`/`validate_jwt_secret()` instead of its own
  inline `_looks_like_local_dev()`/string-comparison logic. Same
  dev-warning message preserved for the local-dev path.
- `engine/routers/auth.py` — admin-password check now raises in production
  via `validate_admin_password()`, instead of only ever warning.
- `engine/main.py` — resolved CORS origins are validated in production
  before `CORSMiddleware` is added; `FORTRESS_API_KEY`'s existing
  warn-only behavior is documented in place (see §5) rather than changed.
- `DEPLOYMENT.md` — production security section rewritten to describe the
  fail-fast behavior instead of warn-only.
- `docs/SECURITY_HARDENING_H3.md` (this file).
- Tests: `tests/backend/test_security_config.py`,
  `tests/backend/test_security_startup_integration.py` (new).

**Not changed**: the authentication model (JWT + httpOnly cookie), the
user model, broker/TOTP credential handling, `market_data_provider.py`,
any scoring/trading logic, or the API-key gate's actual behavior.

## 4. Production-mode detection

```python
def is_production_environment() -> bool:
    return os.getenv("FORTRESS_DB_BACKEND", "").strip().lower() not in {"sqlite", "local"}
```

`FORTRESS_DB_BACKEND=sqlite` or `=local` → development. Anything else
(unset, `neon`, or any other value) → production. This is the *only*
environment variable Fortress uses to make this decision — no second
`FORTRESS_ENV`/`ENVIRONMENT`/etc. flag was added, per the story's explicit
"do not invent multiple competing production flags."

## 5. Secrets validated

| Secret | Enforced in production? | Rationale |
|---|---|---|
| `FORTRESS_JWT_SECRET` | Yes — `RuntimeError` at import | Signs every session token; a known/blank secret lets anyone forge an admin JWT. |
| `FORTRESS_APP_PASSWORD` | Yes — `RuntimeError` at import | The admin account's only credential; a known/blank password is a walk-in admin login. |
| `FORTRESS_CORS_ORIGINS` (resolved list) | Yes — `RuntimeError` at import | A wildcard origin with `allow_credentials=True` defeats the browser's same-origin protections for cookie-based auth. |
| `FORTRESS_API_KEY` | **No — intentionally optional** | Every account-scoped endpoint already requires a valid JWT (cookie or `Authorization: Bearer`) via `auth_utils.get_current_user`; that is the real authentication boundary. `FORTRESS_API_KEY` is a *supplementary* gate for non-browser/machine clients hitting the API directly. Forcing it on in production would change the authentication model (a listed non-goal) for no additional protection on the JWT-protected surface, and would break any legitimate unauthenticated read (e.g. `/api/health`) that's deliberately public. It remains warn-only, documented as a deliberate choice in `engine/main.py` and `DEPLOYMENT.md`. |
| Broker/TOTP credentials (`INDSTOCKS_*`) | Reviewed, no change needed | Read only from environment (`os.getenv`, never hardcoded); `routers/brokers.py` already strips `access_token_encrypted`/`refresh_token_encrypted` before any API response; `indstocks_client.py` logs only generic status messages ("token refreshed successfully", "Token refresh failed: %s") — never the token/secret value; missing credentials make `_indstocks_available()` return `False` and the app falls back to yfinance rather than enabling any unsafe path or blocking startup. No code change was needed here — confirmed by reading `engine/routers/brokers.py` and `engine/utils/indstocks_client.py`. |

## 6. CORS / error-handling findings

- **CORS**: the unset-env default (`http://localhost:3000,http://127.0.0.1:3000`)
  was already safe — never a wildcard. The gap was the *absence* of a
  check on an operator-supplied `FORTRESS_CORS_ORIGINS=*`. Closed via
  `validate_cors_origins()`, enforced in production only.
- **Error/debug exposure**: `engine/main.py`'s existing
  `catch_exceptions_middleware` was reviewed and found already correct —
  it logs the full traceback server-side only (`logger.error`) and returns
  a generic `{"error": "...", "error_id": "..."}` body to the client, never
  a stack trace, environment variable, secret, or connection string. No
  change was needed here.

## 7. Tests run and results

```
PYTHONPATH=.:engine pytest tests/backend -q
410 passed, 4 warnings (pre-existing FastAPI/Starlette deprecation warnings, unrelated)
```

New: `tests/backend/test_security_config.py` (26 tests) — pure
unit tests against `utils/security_config.py`, covering every scenario the
story specifies (A–I):

- A/D: dev mode with a dev/default secret is allowed; production with a
  secure secret passes.
- B/C: production with a default, generic-placeholder, missing, or blank
  JWT secret fails.
- E/F: production with a default/placeholder/missing admin password
  fails; a secure one passes.
- G: the actual secret/password value never appears in the raised
  exception's message, for both individual validators and the centralized
  `validate_security_configuration()`.
- H: production CORS validation rejects a wildcard (alone or mixed with
  real origins) and accepts specific origins (including the app's own
  localhost default).
- I: security validation has no dependency on `INDSTOCKS_*`/broker env
  vars — broker credentials stay optional.

New: `tests/backend/test_security_startup_integration.py` (6 tests) —
proves the actual `import auth_utils` / `import routers.auth` behavior in
a fresh subprocess per case (never `importlib.reload()` in-process, so a
deliberately-failing import can't leave shared module state — e.g.
`auth_utils.SECRET_KEY` — half-initialized for the rest of the test
session): production + default secret/password refuses to import;
production + missing secret refuses to import; production + secure
values imports cleanly; dev mode + default values imports cleanly
(warning only).

No real provider/broker credentials were used or required by any test.

## 8. Remaining security risks

- **Placeholder detection is a finite denylist**, not a strength check —
  `validate_jwt_secret`/`validate_admin_password` reject known-bad values
  but do not enforce a minimum length/entropy on an otherwise-unknown
  value (e.g. `FORTRESS_JWT_SECRET=x` would pass). This story's scope was
  rejecting *known* insecure defaults, not building a general secret-
  strength policy — flagged here as a possible follow-up, not implemented
  to avoid scope creep beyond the story's stated objective.
- **`FORTRESS_API_KEY` remains genuinely optional** (§5) — a deployment
  that wants to block unauthenticated access to public/read-only endpoints
  (e.g. `/api/health`, `/api/universes`) still needs to set it explicitly
  and accept the tradeoff; this was a deliberate choice, not an oversight,
  but is worth re-confirming if the threat model changes.
- **This story validates configuration, not runtime secret handling** —
  e.g. it does not audit every log line in the codebase for accidental
  secret exposure outside the auth/CORS/error-handling paths explicitly
  in scope (per the non-goals: no broad security rewrite, no penetration
  testing).

## 9. Deployment checklist

Before pointing a real deployment (Render, or any `FORTRESS_DB_BACKEND`
other than `sqlite`/`local`) at production traffic:

- [ ] `FORTRESS_JWT_SECRET` set to a unique random value (`openssl rand -hex 32`) — the app will otherwise refuse to start.
- [ ] `FORTRESS_APP_PASSWORD` set to a real password (and consider a non-`admin` `FORTRESS_APP_USERNAME`) — the app will otherwise refuse to start.
- [ ] `FORTRESS_CORS_ORIGINS` set to the exact trusted frontend origin(s), comma-separated, if the default localhost origins don't already match your deployment.
- [ ] Decide on `FORTRESS_API_KEY` deliberately (optional — see §5) rather than leaving it unset by omission.
- [ ] Confirm `FORTRESS_DB_BACKEND` reflects reality (`sqlite`/`local` only for genuine local dev) — this single variable now also gates every check above.
